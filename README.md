CS-300 Data Structures and Algorithms
Advising Assistance Program Summary

The advising assistance project involved developing a software solution for Academic Advising at ABCU to load, validate, search, and sort course catalog data from an external text file. The core problem was ensuring advisors could instantly look up course prerequisites while also printing out an entire catalog in sorted alphanumeric order without performance lag as the catalog expanded. My approach centered on evaluating vectors, hash tables, and binary search trees to balance runtime efficiency against memory overhead. While hash tables offered near instant single lookups, they lacked natural ordering, and vectors required sorting overhead. I chose a binary search tree because it provided logarithmic search times and allowed seamless alphanumeric catalog printing through in-order traversal without needing extra sorting routines. The primary roadblocks I encountered were validating inconsistent comma-delimited input lines and preventing segmentation faults during recursive tree insertions and traversals. I resolved these issues by implementing strict token validation checks on file ingest and carefully tracing pointer references to handle null edge cases. This project fundamentally expanded my approach to software engineering by showing me that selecting the right data structure before writing code solves half the design problem upfront. Moving forward, my code is significantly more maintainable, readable, and adaptable because I separate the internal data storage structure completely from the user-facing interface, allowing future changes to happen cleanly without breaking application logic.


CS-255 System Analysis and Design
DriverPass Project Summary

The DriverPass project involved designing a comprehensive system architecture for a driving school client. They needed a blended approach of object and process modeling to properly organize their new application. I mapped out the core structure using various UML diagrams like activity, sequence, and class diagrams to visualize exactly how users would interact with the platform. I'm particularly proud of how the maintenance process turned out. I proposed a built-in ticketing system for the staff that integrated directly with automated monitoring tools for tracking crashes and database errors. If I could revise one part of my work, I'd definitely improve the client presentation. Breaking down complex UML diagrams for stakeholders with no technical experience is always a fun challenge. I think adding a few more simplified visual aids would really smooth out that communication. I interpreted the user's needs by closely analyzing the business requirements document and mapping every technical feature back to one core goal. It's incredibly important to consider the user's needs when designing because a system is completely useless if it doesn't solve their actual problems. My approach to designing software relies heavily on blueprinting everything out before writing a single line of code. In the future, I'll definitely keep using sequence diagrams to analyze and design systems. They're perfect for visualizing the flow of data and identifying bottlenecks early in the process.



CS-250 Software Development Lifecycle

I interpret user needs by looking at the software entirely from the end user's perspective. Creating user stories helps a lot with this. They force you to define exactly who is using the application and what their specific goal is. For the SNHU Travel project for ChadaTech, breaking the requirements down into distinct user stories made it so much easier to prioritize the right features during our development sprints. I approach development by focusing on iterative progress rather than trying to build everything at once. Working through the Sprint Review and Retrospective showed me the value of adapting quickly when unexpected project interruptions happen. I'm planning to incorporate daily stand-ups and regular sprint retrospectives into my future development work. They keep the whole team aligned and catch minor issues before they become major roadblocks. Being a good team member in software development means communicating clearly and being flexible when Agile practices demand a shift in priorities. During my experience acting as the Scrum Master, I found that listening to the developers and helping remove their obstacles is just as important as writing the code itself. A solid team collaborates closely and always supports each other through changing requirements.
